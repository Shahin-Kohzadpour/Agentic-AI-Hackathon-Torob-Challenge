# معماری و تصمیم‌های نسخهٔ نهایی

## مسیر تصمیم

متن کاربر ← استخراج نیاز محدود با ابزار ساختاریافتهٔ مدل ← جست‌وجوی FTS5 در کل کاتالوگ ← مقایسهٔ مشخصات ثبت‌شده ← انتخاب محصول با ID ← اعمال policy مشترک بودجه/پرداخت/شعاع/زمان ← بررسی فروشنده با job پایدار ← جایگزین‌یابی یا کارت مراجعه.

مدل فقط query و نیاز را استخراج می‌کند. شناسه، قیمت، فروشگاه، زمان، منبع و مجوز ساخت کارت از سرویس‌های سرور می‌آیند. فرمان‌های روشن در چت، مانند «ارزان‌ترین فروشگاه را بررسی کن»، همان transition کنترل‌شدهٔ دکمه‌ها را فراخوانی می‌کنند. متن OCR یا فروشنده وارد مسیر فرمان کاربر نمی‌شود.

## ساختار

- `src/lib/services/catalog.ts`: FTS، مدل/واریانت دقیق، حذف لوازم جانبی نامربوط، آفرهای چندگانه و شمارش فروشگاه متمایز.
- `src/lib/policy.ts`: پول صحیح تومان، ترب‌پی حضوری با provider/channel/bounds/category، ساعات تهران و حاشیهٔ مراجعه.
- `src/lib/session.ts` و `workflow.ts`: نشست HttpOnly، SQLite، optimistic version، transaction، بررسی قابل لغو، reset و حذف پاسخ دیررس.
- `seller-simulator.ts`: شش نتیجهٔ مشخص و دائماً برچسب‌خورده؛ حالت دمو به نشست همان کاربر محدود است.
- `ShoppingCanvas`, `PreferencePanel`, `ChatInterface`: کنترل مشترک فرم/چت، مقایسه، نقشه، توضیح علت و اقدام بعدی.
- `src/data/shopping-areas.json`: منابع بیرونی مراکز خرید با URL و تاریخ؛ از استنباط تراکم فروشگاه در دیتاست متمایز است.

## چرا این ابزارها

Next.js/React برای یک رابط و API مشترک؛ Node 24 با SQLite داخلی برای کاهش اجزای استقرار؛ FTS5 و `product_stats` برای جست‌وجوی سریع کاتالوگ ثابت؛ OpenAI SDK با endpoint سازگار DeepSeek برای استخراج schema و vision؛ Leaflet برای نمایش موقعیت و نشان برای مسیر واقعی.

چارچوب چندایجنتی و vector database اضافه نشده‌اند: این مسئله ابتدا به تطبیق دقیق مدل و شروط قابل اثبات نیاز دارد. گردش کار صریح و persisted، لغو/نسخه/خطا را قابل آزمون نگه می‌دارد. خروجی مدل به ابزار محدود است و timeout/fallback دارد. آموزش اختصاصی مدل با توجه به دادهٔ ساختاریافته و مهلت چالش توجیه نشد.

## یکپارچگی و دوام

کاتالوگ فقط خواندنی است. import به فایل موقت انجام و FK/integrity/count/source hashes بررسی می‌شود. ۱۵۰۸۳ قیمت خالی اصلی و ۱۱ قیمت صفر/نامعتبر به‌عنوان مبلغ نامعلوم نگهداری شده‌اند؛ مقدار خام حذف نشده است. هیچ آفر یا ارتباطی برای پاک‌سازی قیمت حذف نشده است.

نشست‌ها و بررسی‌ها در `workflow.db` روی دیسک پایدار هستند. mutationها transaction و version دارند. تغییر شروط بررسی ناسازگار را باطل می‌کند؛ گفت‌وگوی صرفاً توضیحی، مدرک معتبر بررسی را از بین نمی‌برد. آخرین نتیجهٔ معتبر یک فروشگاه برای همان محصول و شروط بر شکست قدیمی اولویت دارد.

startup از workflow با SQLite backup API، شامل دادهٔ committed در WAL، snapshot می‌گیرد. کاتالوگ نسخه‌دار است تا rollback به دادهٔ قبلی ممکن باشد. این طراحی برای یک replica است؛ افزایش replica به اشتراک پایگاه داده و rate limiting توزیع‌شده نیاز دارد.

## محدودیت‌های روشن

موجودی و تماس واقعی فروشنده در اختیار چالش نیست؛ ارتباط شبیه‌سازی است. کیفیت تجربی محصول و امتیاز مشتری ساخته نمی‌شود. مشخصات ناقص با برچسب نامعلوم می‌ماند. تشخیص گفتار به مرورگر وابسته است و آزمون خودکار حاضر دقت گفتار فارسی را اندازه نگرفته است. پیشنهاد مرکز خرید، موجودی یا پذیرندگی اقساط یک فروشگاه را تضمین نمی‌کند.
